## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本实验围绕内核线程的创建与调度展开，在前面实验已经具备的物理内存管理、页表机制和中断处理能力上，使内核能够管理多个执行实体，并让它们轮流使用 CPU。整个实验按照“虚拟内存页操作 → 进程创建与初始化 → 进程调度与上下文切换”的顺序推进，各模块分别解决运行空间如何准备、线程如何创建和线程如何执行的问题。

内存管理为线程运行提供基础。页表记录虚拟地址到物理页的对应关系，映射的建立、替换和撤销需要同时维护页表项、物理页引用计数和 TLB。框架提供的 `mm_struct`、`vma_struct` 进一步描述虚拟地址空间及其区域属性，将地址空间的逻辑组织与具体页映射联系起来。本实验中的内核线程共享内核地址空间，每个线程拥有独立的内核栈、寄存器上下文和控制块，因此能够在共享代码与数据的同时保存各自的执行进度。

在线程管理层面，系统使用 `proc_struct` 统一记录线程的身份、状态、资源和运行现场。创建线程时，内核先分配控制块和内核栈，再构造首次运行所需的上下文，最后将线程登记为可运行状态。调度器随后从可运行线程中选择目标，通过上下文切换将 CPU 交给它。这样，启动阶段的一条执行流就逐步扩展为由内核统一管理的多条执行流。

### 3.2 功能的逐步实现

#### 3.2.1 完善虚拟内存页操作，建立线程运行所需的内存基础

首先在 `kern/mm/pmm.c` 中实现 `page_insert()` 和 `page_remove()`。`page_insert()` 借助 `get_pte()` 定位或创建页表路径，建立指定虚拟地址到物理页的映射，并处理权限更新、同页重复映射和替换旧页等情况。`page_remove()` 撤销已有映射，减少对应物理页的引用计数，并在引用归零时释放该页。页表发生变化后同步刷新 TLB，使 CPU 后续访问使用更新后的映射关系。

这一阶段把物理页分配能力与虚拟地址访问连接起来。结合框架提供的虚拟内存区域管理和 `kmalloc()`、`kfree()`，后续模块就能够分配线程控制块、准备内核栈，并使用已经建立的内核地址空间。

#### 3.2.2 初始化进程管理结构，将启动执行流纳入线程管理

接着通过 `alloc_proc()` 分配并初始化 `proc_struct`，为线程设置状态、PID、内核栈指针、上下文和链表节点等基础字段。控制块使内核能够用统一的数据结构描述不同线程，也为后续查找、登记和调度提供依据。

`proc_init()` 初始化进程链表和 PID 哈希表，并将当前从 `kern_init()` 延续下来的执行现场包装为第 0 个内核线程 `idleproc`。它复用启动栈 `bootstack`，成为 `current` 指向的当前线程，同时设置重调度标记。完成这一步后，内核启动过程便拥有了明确的线程身份，可以通过统一的调度接口让出 CPU。

#### 3.2.3 创建 `initproc`，准备新线程首次运行的完整现场

在 `idleproc` 的基础上，`proc_init()` 调用 `kernel_thread()` 创建执行 `init_main()` 的线程 `initproc`。`kernel_thread()` 将线程入口函数、参数和处理器状态组织成临时中断帧，再交给 `do_fork()` 完成创建。

`do_fork()` 依次分配控制块和独立内核栈，处理地址空间关系，并调用 `copy_thread()` 设置新线程的运行现场。本实验中，`copy_mm()` 维持内核线程共享内核地址空间的关系。`copy_thread()` 将中断帧安放在新线程的内核栈上，并设置控制块中的上下文，使线程首次被切换执行时能够进入 `forkret`。随后，内核分配 PID、建立父子关系、将线程加入管理结构，并通过 `wakeup_proc()` 将其置为 `PROC_RUNNABLE` 状态。

这一阶段完成后，系统同时拥有正在执行的 `idleproc` 和等待调度的 `initproc`。新线程的资源与入口现场已经准备好，接下来需要由调度器赋予它执行机会。

#### 3.2.4 实现调度与上下文切换，让新线程真正获得 CPU

内核完成各子系统初始化后，进入 `cpu_idle()`。当 `idleproc` 检测到 `need_resched` 被置位时，调用 `schedule()`，从进程链表中寻找下一个处于 `PROC_RUNNABLE` 状态的线程。调度器按照链表顺序选择线程，找不到可运行线程时选择 `idleproc`。

选定目标后，`proc_run()` 在屏蔽中断的临界区内更新 `current`，设置目标线程使用的页表，并调用 `switch_to()`。`switch_to()` 保存原线程的 `ra`、`sp` 和 `s0` 至 `s11`，再恢复目标线程的对应寄存器。原线程的执行位置因此得以保留，目标线程则从自己的上下文继续执行。

对首次运行的 `initproc`，创建阶段预设的上下文使执行流沿以下路径进入线程函数：

```text
switch_to → forkret → forkrets → __trapret
          → sret → kernel_thread_entry → init_main
```

其中，`forkrets` 将栈指针切到新线程的中断帧，`__trapret` 恢复寄存器和处理器状态，`sret` 跳转到预设的 `kernel_thread_entry`。该入口取出线程参数并调用 `init_main()`，由此完成从启动线程到新建内核线程的第一次执行权交接。

### 功能模块一：虚拟内存页操作功能

**负责人：** 2411268-黄泽恺

#### 模块功能描述

**需要实现/修改的函数：**

```c
int page_insert(pde_t *pgdir, struct Page *page, uintptr_t la, uint32_t perm);
void page_remove(pde_t *pgdir, uintptr_t la);
```

**功能说明：**

本模块负责维护 Sv39 多级页表中虚拟地址与物理页之间的映射关系，提供建立、更新和撤销单页映射的接口。操作过程中，需要使页表项、物理页引用计数和 TLB 保持一致，为内核访存、页表自检和后续地址空间管理提供基础。

`page_insert()` 根据指定的虚拟地址定位末级页表项，必要时创建中间级页表。目标地址尚未映射时，建立映射并增加物理页引用计数；已经映射到同一物理页时，更新权限并保持引用计数稳定；已经映射到另一物理页时，替换映射并减少旧页引用计数，旧页引用归零后释放。如果页表分配失败，函数返回 `-E_NO_MEM`，并回收本次操作已经分配的中间级页表页，恢复原目录项。

`page_remove()` 撤销指定虚拟地址的映射，清空末级页表项并减少原物理页的引用计数，引用归零时将该页归还给物理内存管理器。目标地址没有有效映射时直接返回，因此重复删除能够保持引用计数和空闲页统计稳定。

本模块通过 `get_pte()`、`get_page()` 和页表项转换接口访问已有页表结构，通过物理页分配器完成页表页的分配与物理页回收。实现中新增了内部辅助函数 `sync_page_table()`，复用 `tlb_invalidate()` 和 `flush_tlb()` 完成地址翻译缓存同步。上层的 `check_pgdir()`、`check_boot_pgdir()` 和 PMM 测试通过这些接口检查映射关系、权限、引用计数及实际访存结果，后续线程管理则在准备好的内核地址空间中分配和使用控制块、内核栈等资源。

### `page_insert()`

**Pre-Condition**  
物理页分配器已初始化。`pgdir` 指向可访问的 Sv39 根页表，`page` 是已分配且由物理页管理器管理的页描述符。`la` 可带页内偏移，操作目标是它所在的 4 KiB 页。已有映射属于由引用计数管理的末级映射。

**Post-Condition**  
成功返回 `0`。目标 PTE 指向 `page`，设置 `PTE_V`，权限按本次 `perm` 设置。旧映射独有的权限随更新清除。同一物理页通过多个虚拟地址映射时，每个映射各占一次引用。

- **Case 1 · 目标无有效映射**

**Pre-Condition**

- **Case 1 · 页表路径不存在，或末级 PTE 无效**  
  直接返回。查找过程不分配页表页，也不修改引用计数。
- **Case 2 · 末级 PTE 有效**

### 功能模块二：进程创建与初始化

**负责人** 黄子恒-2412414

#### 模块功能描述

本模块在 [`code/kern/process/proc.c`](../code/kern/process/proc.c#L221) 的 `LAB4 function2 2412414` 区块实现内核线程创建和初始化。启动时，`proc_init()` 先用一个 PCB 表示正在运行的 `idleproc`，再创建可供调度的 `initproc`。创建链路为 `proc_init() → kernel_thread() → do_fork()`。新线程的内核栈和执行现场由模块二准备，随后由调度器切换执行。

| 函数 | 实现要点 |
|---|---|
| `alloc_proc()` | 分配并初始化 PCB。初始状态为 `PROC_UNINIT`，PID 为 `-1`，页表物理地址为 `boot_pgdir_pa`。分配失败时返回 `NULL`。 |
| `copy_mm()` | 当前实验创建内核线程，父子线程共享启动页表，`mm` 保持为 `NULL`。该路径返回 `0`。 |
| `copy_thread()` | 在子线程内核栈高端保存中断帧副本并将 `a0` 清零。设置 `context.ra` 指向 `forkret`，`context.sp` 指向帧副本。帧中的 `gpr.sp` 用于 `sret` 后的实际执行。 |

### 功能模块三：进程调度

#### 模块功能描述

**需要实现/修改的函数：**

```c
void cpu_idle(void);
void schedule(void);
void proc_run(struct proc_struct *proc);
void switch_to(struct context *from, struct context *to);
```

**功能说明：**

`cpu_idle()` 循环检查当前线程的 `need_resched`。初始化完成后，`current` 指向 `idleproc`，调度标志已置位，空闲线程随即调用 `schedule()`。调度器在关中断期间清除当前线程的调度请求，沿 `proc_list` 寻找 `PROC_RUNNABLE` 线程。当前是空闲线程时从表头开始，当前是普通线程时从其后继开始，越过表尾后继续查找。如果只有当前普通线程就绪，就继续执行它。如果普通线程均不可运行，就选 `idleproc`。每次选中线程都将其 `runs` 加一，目标变化时才调用 `proc_run()`。

`proc_run()` 保存本地中断状态，将 `current` 指向目标线程，把目标根页表的物理页号写入 Sv39 模式的 `satp`，刷新 TLB 后调用 `switch_to()`。汇编按 `struct context` 的字段顺序保存旧线程的 `ra`、`sp` 和 `s0` 至 `s11`，再从新线程的上下文恢复这 14 个寄存器。`ret` 使用恢复后的 `ra`，因此曾经被切走的线程会接着执行原来的 `switch_to()` 调用点之后的代码，并恢复该线程保存的中断状态。

首次运行的 `initproc` 使用模块二预设的内核栈和中断帧。`switch_to()` 恢复的 `ra` 指向 `forkret()`，`sp` 指向中断帧。`forkret()` 经 `forkrets` 进入异常返回代码，将中断帧中的返回地址和状态装入对应的 CSR。`sret` 回到 `kernel_thread_entry`，再由它将保存的参数传给 `init_main()`。

#### 1. 说明语句 `local_intr_save(intr_flag); ... local_intr_restore(intr_flag);` 是如何实现开关中断的

这两个宏定义在 kern/sync/sync.h 中。local_intr_save(intr_flag) 检查 sstatus 寄存器的 SIE 位，将进入临界区前的中断状态保存到 intr_flag，并关闭当前 CPU 的监督者级中断。local_intr_restore(intr_flag) 根据保存的状态决定是否重新开启中断。

```c
static inline bool __intr_save(void) {
    if (read_csr(sstatus) & SSTATUS_SIE) {
        intr_disable();
        return 1;
    }
    return 0;
}

static inline void __intr_restore(bool flag) {
    if (flag) {
        intr_enable();
    }
}

#define local_intr_save(x) \
    do {                   \
        x = __intr_save();  \
    } while (0)

#define local_intr_restore(x) __intr_restore(x);
```

具体的开关操作位于 `kern/driver/intr.c` 中：

```c
void intr_enable(void) {
    set_csr(sstatus, SSTATUS_SIE);
}

void intr_disable(void) {
    clear_csr(sstatus, SSTATUS_SIE);
}
```

进入前中断开启，退出时就重新开启；进入前已经关闭，退出时继续保持关闭。这使临界区能够嵌套使用，内层退出时不会提前打开外层关闭的中断。项目中的物理页分配与释放函数通过这种方式保护空闲链表和页数统计。

#### 2. 深入理解不同分页模式的工作原理

##### 2.1 `get_pte()` 中的两段代码为什么如此相像

Sv32、Sv39 和 Sv48 都采用多级页表。对于普通的 4 KiB 页映射，虚拟地址由多级页表索引和 12 位页内偏移组成。处理器从 `satp` 指定的根页表开始，逐级利用索引取得下一层页表，最终由末级页表项确定物理页，页内偏移保持原值。三种模式的主要差异如下。

| 分页模式 | 适用架构 | 页表层数 | 各级索引位数 | 页表项大小 | 每张页表的项数 |
|---|---|---:|---|---:|---:|
| Sv32 | RV32 | 2 | 10 + 10 | 4 字节 | 1024 |
| Sv39 | RV64 | 3 | 9 + 9 + 9 | 8 字节 | 512 |
| Sv48 | RV64 | 4 | 9 + 9 + 9 + 9 | 8 字节 | 512 |

当前项目使用 Sv39，`get_pte()` 中的遍历过程为：

```text
pgdir
  └─ PDX1(la)，取虚拟地址的第 38～30 位
       └─ 下一层页表
            └─ PDX0(la)，取第 29～21 位
                 └─ 末级页表
                      └─ PTX(la)，取第 20～12 位
                           └─ 返回对应末级 PTE 的地址
```

函数中的第一段代码处理根页表的 PDX1(la) 项，第二段代码处理下一层页表的 PDX0(la) 项。两段代码都要检查目录项是否有效，在允许创建且目录项缺失时，分配一个页表页、初始化并挂接到上一级。

因此，两段代码相像的原因是多级页表的各层具有相同的组织方式，逐层查找和创建的操作也基本相同。Sv32 到达末级页表需要经过一层目录，Sv39 需要两层，Sv48 则需要三层。

##### 2.2 是否应该将页表项查找和页表页分配拆开

我们认为当前实验中合并实现是合理的。当前 `get_pte()` 使用 `create` 参数控制行为：

```c
pte_t *get_pte(pde_t *pgdir, uintptr_t la, bool create);
```

create = 0，只查找已有页表，路径缺失时返回 NULL。

create = 1，允许分配缺失的中间级页表，分配失败时返回 NULL。

这样可以复用页表遍历逻辑，调用也比较方便。page_remove() 使用只读查找，page_insert() 则在需要时创建页表路径。函数返回的是末级页表项的地址，该项是否已有有效映射还需进一步检查。

如果后续功能更加复杂，可以拆成独立的查找接口和创建接口，让调用者明确一次操作是否会分配内存。同时，创建接口可以统一负责分配失败后的清理。例如，当前 get_pte() 可能在第一张页表分配成功、第二张分配失败后留下部分路径，本次 page_insert() 就需要负责回收。因此，本实验可以保留现有接口，后续扩展时再根据资源管理需求拆分。

## 六、实验总结与收获

### 对操作系统的理解

#### 6.1 本实验的重要知识点及其与 OS 原理的联系

| 知识点 | 本实验中的体现 | 与 OS 原理的联系及差异 |
|---|---|---|
| 多级页表与地址翻译 | 使用 Sv39 三级页表，通过 `get_pte()` 定位末级页表项，利用 `page_insert()` 和 `page_remove()` 管理映射 | 多级页表通过分层组织减少稀疏地址空间的页表开销。本实验主要操作普通 4 KiB 页的映射，虚拟地址空间的扩展还可以结合大页、按需分页等机制。 |
| 物理页引用计数与资源回收 | 建立、替换和撤销映射时同步维护物理页引用计数，引用归零后释放物理页 | 一个物理页可以被多个虚拟地址引用，撤销其中一条映射后，需要根据剩余引用决定是否回收。引用计数把映射关系与物理页生命周期联系起来。 |
| 页表与 TLB 的一致性 | 页表项更新后刷新相应的地址翻译缓存 | 页表保存地址映射，TLB 缓存翻译结果。修改页表后需要使旧缓存失效，CPU 后续访问才能使用新的映射和权限。 |
| 进程与线程的组织 | 使用 `proc_struct` 描述线程，记录 PID、状态、内核栈、上下文及父子关系 | 控制块是操作系统管理执行实体的基础。本实验中的内核线程共享内核地址空间，各自拥有独立的栈和执行现场；用户进程还需要管理自己的用户地址空间。 |
| 调度与上下文切换 | `schedule()` 选择可运行线程，`proc_run()` 和 `switch_to()` 完成执行权交接 | 调度负责选择运行对象，上下文切换负责保存和恢复现场。本实验采用沿进程链表查找的简单调度方式，并利用函数调用约定保存恢复所需的关键寄存器。 |
| 临界区与中断控制 | 通过 `local_intr_save()` 和 `local_intr_restore()` 保护物理页管理和线程切换中的关键操作 | 临界区保护用于避免共享状态在更新过程中被并发访问。关闭本地中断能够控制当前 CPU 上的中断交错，多核共享数据还需要锁等同步机制。 |

本实验使我们进一步理解了“线程能够运行”所需的条件。创建线程时，除了分配控制块，还需要准备内核栈、中断帧和上下文。调度发生后，新线程沿预设的恢复路径进入入口函数，已经运行过的线程则从此前保存的位置继续执行。线程的创建、调度和现场恢复因此构成了相互衔接的过程。

#### 6.2 OS 原理中重要、但本实验尚未完整涉及的知识点

1. **用户进程与特权级隔离。** 用户程序需要独立的用户地址空间，并通过系统调用进入内核，涉及用户态与内核态之间的切换、访问权限检查和参数验证。

2. **按需分页、页面置换与写时复制。** 更完整的虚拟内存系统需要在缺页时分配或调入页面，在内存紧张时选择页面换出，并通过写时复制减少进程复制的开销。本实验主要完成已有物理页的映射维护。

3. **抢占式调度与复杂调度策略。** 时间片、优先级、公平性和响应时间都会影响调度效果。本实验重点建立基本的调度与切换机制，更复杂的策略需要进一步结合时钟和调度数据结构实现。

4. **完整的进程生命周期管理。** 进程退出后还需要释放地址空间、改变状态、通知父进程并回收资源。当前模板中的 `do_exit()` 通过 `panic()` 结束执行，退出与等待机制仍有进一步扩展的空间。

5. **阻塞唤醒与多核同步。** 线程等待设备或共享资源时，需要睡眠队列和唤醒机制；多个 CPU 同时访问共享数据时，还需要考虑锁、原子操作及跨核 TLB 同步。

### AI 协作开发的经验

本次实验中，我们按照 `[PROMPT]`、`[RELY]`、`[GUARANTEE]` 和 `[SPECIFICATION]` 四段式框架组织提示词。先说明模块需要提供的能力，再列出真实接口和行为要求，能够帮助 AI 将映射、引用计数、错误处理和 TLB 同步放在同一个功能目标下考虑。

我们也认识到，提示词中的上下文需要与工程代码一致。例如，项目将 `bool` 定义为 `int`，首次生成代码使用了尚未定义的 `true`、`false`，导致编译失败。对照现有代码改用 `1`、`0` 后，模块通过编译。这说明基础类型、宏和函数签名也需要纳入上下文检查。

验证代码时，应将需求转化为具体状态检查。对于页映射模块，除了确认映射能够建立，还要检查同页重插后引用计数是否稳定、替换映射后旧页是否回收、重复删除是否安全，以及页表分配失败后资源是否恢复。通过这些场景，才能判断实现是否覆盖了完整的操作过程。

AI 帮助我们完成了需求整理、代码生成和边界场景验证。我们则需要持续核对代码是否符合项目约定，并理解每个接口维护的系统状态，使提示词、实现和测试结果能够相互对应。
